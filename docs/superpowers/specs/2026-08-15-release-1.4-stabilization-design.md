# WGJ 1.4.0 Stabilization Design

Date: 2026-08-15
Status: Approved

## Objective

Prepare WGJ 1.4.0 as an app-wide stabilization release by fixing every confirmed P1 and P2 finding from the 1.3.0 audit, completing the required release-validation gaps, and making Development and Production safe to install and test side by side.

The release remains local-first. Active workout progress and template work-in-progress persist locally during editing. CloudKit remains best-effort and may run only at explicit save boundaries. SwiftUI views remain presentation-focused; persistence, retry, projection, and migration behavior belongs in repositories or services.

## Release Scope

This design covers:

- Complete Development and Production storage isolation.
- Durable template drafts and race-free template saves.
- Correct, bounded history pagination and analytics projection retries.
- Recoverable Delete My Data and persistent-store reset behavior.
- Progress refresh consistency.
- Database-bounded history loading, lightweight Progress loading, and cached chart projection.
- Safe template hydration and local-only template repair.
- Reliable catalog priming and explicit settings backup boundaries.
- Marketing version 1.4.0, build 1 for the new App Store version train.
- File-backed v1.3 migration coverage, expanded UI smoke coverage, Release builds, signed-device validation, and targeted performance profiling.

This design does not cover:

- New product features unrelated to stabilization.
- A visual redesign of existing screens.
- Broad background synchronization.
- Copying Production data into Development.
- Running destructive validation against the installed Production app or its real data.
- Unverified performance rewrites that are not supported by code evidence or profiling.

## Template Durability and Save Serialization

### Local draft journal

Template editing uses an atomic, local-only draft journal owned by a dedicated service rather than the SwiftUI view. A draft contains the complete editor value state, template identity or new-template identity, and a monotonically increasing revision.

Meaningful editor changes schedule a coalesced local write. Scene deactivation flushes the latest revision synchronously enough to reach the atomic file-replacement boundary before suspension. Draft writes never save SwiftData models and never schedule CloudKit.

Opening the editor resolves its initial state before enabling controls:

1. Load the persisted template snapshot when editing an existing template.
2. Load any compatible newer draft journal.
3. Present the newer valid value state.

The editor does not accept changes while this initial resolution is incomplete, preventing late hydration from overwriting early input.

Save commits the newest editor revision through the repository. After a successful commit, the journal is removed only if its revision is not newer than the committed request. Cancel explicitly discards the draft after user intent is confirmed by the existing dismissal flow. Process termination or background suspension leaves the draft available for restoration.

### Revisioned save state

Every save request captures an immutable value snapshot and revision. Completion may dismiss or reload the editor only when that revision is still current. If the user edits while an earlier request is in flight, the completion cannot overwrite, dismiss, or clear the newer revision. The newer state remains visible and can be committed by the serialized save coordinator.

Template detail follows the same revision rule. Existing-template hydration cannot mutate an editor after user-owned state has advanced.

### Local-only repair

Default set-plan repair and legacy template normalization use an explicit local maintenance save boundary. Repair may update local persistence but cannot schedule a template-saved CloudKit backup. A user-initiated template save remains the explicit backup boundary.

## History Correctness and Throughput

### Composite pagination cursor

Completed-workout ordering is total and deterministic: completion date descending, then stable workout UUID descending. Pagination carries both values in a `HistoryCursor`.

The next-page predicate selects records where:

- Completion date is earlier than the cursor date, or
- Completion date equals the cursor date and UUID is ordered after the cursor boundary according to the selected descending order.

This prevents skipped or duplicated workouts when multiple sessions share an identical completion timestamp.

### Database-bounded pages

History page loading applies the predicate, sort descriptors, and fetch limit in the persistence query. It does not fetch the complete completed-workout table and truncate in memory. Related exercise and set data is fetched in batches for the selected page rather than through per-row queries.

If SwiftData cannot express a required tuple predicate reliably for the deployed OS floor, the repository uses a bounded overlap at the date boundary and applies the UUID tie-break in memory. The overlap remains bounded and covered by identical-timestamp tests; a full-table fetch is not permitted.

### Analytics retry policy

History analytics projection work records attempt count, next eligible attempt, and terminal status. Transient failures use bounded exponential backoff with jitter. The retry count is finite. Permanent errors and exhausted transient errors enter a terminal inspectable state instead of immediately requeueing forever.

Successful projection clears retry metadata. A subsequent relevant workout mutation may explicitly reactivate a terminal item because the underlying input changed.

## Destructive Data Operations

### Delete My Data

Delete My Data follows an ordered recovery-safe transaction:

1. Prevent launch restoration from consuming existing backup artifacts.
2. Delete local database content through the deletion service.
3. Confirm the local deletion commit.
4. Attempt local snapshot, widget, and CloudKit artifact cleanup.
5. Persist retry work for any cleanup that did not complete.

Once local deletion commits, the operation is reported as deleted. Later cleanup failure produces a warning and retained retry state; it does not falsely report that the database deletion failed. Restore sources remain invalidated so stale artifacts cannot repopulate deleted data on the next launch.

### Persistent-store reset

Scheduled store reset tracks each configured store and sidecar as an explicit target. The retry marker is cleared only after every required target is confirmed absent. Partial file-removal failure preserves the marker, records the failed targets, and retries on the next safe launch. Errors are not suppressed with `try?` at the decision boundary.

Reset validation covers all four production store topologies and their SQLite sidecars without using broad or unresolved filesystem targets.

## Refresh and Explicit Backup Boundaries

Progress subscribes to the same workout-history mutation broadcaster used by History. When Progress is visible, a relevant mutation invalidates and reloads its snapshot. When it is not visible, invalidation is retained and the next activation performs one load.

Catalog bootstrap marks seed priming and completion only after the import succeeds. Failure preserves the unprimed state and exposes the existing recoverable retry path.

Settings persistence remains local and serialized. After a successful settings commit, a coalesced explicit `.settingsSaved` backup request is scheduled. Rapid setting changes collapse into one best-effort backup. Failed local persistence never schedules backup, and CloudKit never runs directly from control interaction handlers.

## Progress and Chart Performance

### Lightweight Progress loading

The initial Progress snapshot loads only fields required to list and select comparison candidates. It does not hydrate every exercise and set from every completed workout. Full exercise/set history is requested only for the two selected comparison targets and is cancelled or rejected when selection generations change.

The lightweight and hydrated value types remain immutable and Sendable. SwiftData models do not cross actor boundaries.

### Cached chart projection

Exercise chart series, summaries, availability, and selection lookup tables are projected outside SwiftUI `body`. Cache keys include stable exercise identity, source-history revision, metric, range, and display-unit inputs.

Changing only the selected chart point reads the existing lookup table and does not rebuild the full series. A relevant workout mutation or input change invalidates only affected cache entries. Cache ownership belongs to the controller or service layer, not ad hoc `@State` computation in the view.

### Evidence boundary

Non-lazy active-workout and template stacks, background dirty-field consolidation, metrics-cache retention, History detail hydration, calendar request coalescing, and profile backup decoding remain profiling or test hypotheses unless runtime evidence demonstrates a release-impacting problem. They receive targeted validation but are not rewritten speculatively as part of the confirmed P1/P2 batch.

## Loading and Error Handling

- Template restoration uses a bounded loading state and preserves the last valid local draft if persisted-template loading fails.
- Save cancellation is not surfaced as an error unless user action is required.
- History paging retains the last valid page when a later page fails and offers retry from the same composite cursor.
- Projection terminal failures are observable through diagnostics and do not block ordinary history rendering.
- Delete cleanup warnings explain that personal data was deleted locally while cleanup will retry.
- Development signing errors identify the exact missing App ID, App Group, CloudKit container, or regenerated profile requirement.
- Performance projection cancellation is expected and is never shown as a user-facing failure.

## Migration and Release Validation

### File-backed v1.3 fixture

Migration coverage includes a checked-in or deterministically generated v1.3 fixture representing the real four-store topology and v1.3 schema. The test copies the fixture into a temporary application-support layout, opens it with the 1.4 model/container configuration, and validates representative data from every store.

The fixture includes:

- User settings and profile state.
- Exercises and aliases.
- Templates with exercises and set plans.
- Completed workout history with sets.
- An active-workout snapshot where supported by the v1.3 format.

Validation proves migration preserves identifiers, relationships, completion dates, units, cardio-compatible data, template plans, and settings. It also verifies a second open is idempotent and does not duplicate seeded or migrated content.

### Automated tests

Focused tests cover:

- Atomic template journal round-trip, replacement, corruption handling, discard, and revision-safe cleanup.
- Process-restoration behavior for new and existing templates.
- Save completion racing a newer edit.
- Hydration completion racing early input.
- Local-only template repair with no backup scheduling.
- Composite cursor paging with identical timestamps across multiple page boundaries.
- Database page limits and bounded boundary overlap when used.
- Batched child hydration.
- Retry delay growth, jitter bounds, retry exhaustion, terminal state, and mutation reactivation.
- Delete success with snapshot or CloudKit cleanup failure.
- Restore invalidation after committed deletion.
- Partial four-store reset retaining its marker.
- Progress notification invalidation and inactive-tab coalescing.
- Catalog import failure preserving retry eligibility.
- Settings persistence success/failure and backup coalescing.
- Lightweight Progress loading and stale hydration rejection.
- Chart cache hits, invalidation, and point-selection behavior.
- Debug/Release capability configuration and environment-specific identifiers.
- File-backed v1.3 four-store migration and second-open idempotence.

### UI smoke tests

The isolated Development app gains smoke coverage for:

- Launch and first-run catalog initialization.
- Start workout, edit a set, background and foreground, restore, and finish.
- Edit a template, terminate before save, relaunch, restore the draft, and save.
- Race a template save with a later edit and confirm the latest state remains.
- Page History across identical completion timestamps.
- Mutate workout history and confirm Progress refreshes.
- Delete My Data with injected cleanup failure and relaunch without restoration.
- Settings changes persisting locally and coalescing a backup request.
- Backup and restore against the Development CloudKit container only.

Tests use launch arguments and deterministic local fixtures. They do not sign into, launch, overwrite, or delete data from the Production installation.

### Build, signing, and runtime validation

Required gates are:

1. Focused tests pass after each implementation task.
2. Full unit and UI suites pass on the selected Simulator.
3. Debug `WGJ Dev` build resolves only Development entitlements.
4. Release `WGJ` build resolves only Production entitlements.
5. Xcode Analyze passes for the normal scheme configuration.
6. Signed `WGJ Dev` installs beside the App Store Production app on the connected device.
7. Codesign inspection of the installed Development app and widget confirms only `.dev` App Group and CloudKit identifiers.
8. Launching Development shows fresh isolated local data and cannot see Production widget state or backups.
9. A Release archive validates matching app/widget version 1.4.0 build 1 without being installed over the Production app.

### Performance validation

Release-configuration profiling uses the isolated Development app and deterministic large fixtures:

- A workout with enough exercises and sets to stress active-workout rendering.
- At least 1,000 completed workouts for History and Progress.
- Repeated History paging across equal timestamps.
- Progress load followed by selection of two exercises.
- Exercise-detail metric and range switching plus chart-point dragging.
- Profile backup-summary loading.

Collect launch/runtime traces and memory evidence where supported. Compare query counts, main-thread time, view-update behavior, peak memory, and interaction responsiveness before and after. Any remaining hypothesis is reported with evidence and ranked separately; it is not silently expanded into the release scope.

## Acceptance Criteria

The stabilization sweep is complete when:

- `WeGoJim` and `WeGoJim Dev` install side by side and cannot access each other's local, widget, or CloudKit data.
- Development signing profiles regenerate successfully with only the Development resources.
- Template work survives termination and newer edits cannot be lost to older async completion.
- History pages neither skip nor duplicate equal-timestamp sessions and do not fetch the full history table for each page.
- Analytics projection cannot enter an immediate infinite retry loop.
- Committed data deletion cannot be reported as a total failure or later undone by stale restore artifacts.
- Partial store reset remains scheduled until all four store families are removed.
- Progress refreshes after relevant workout mutations.
- Initial Progress and chart interactions avoid the confirmed broad hydration and render-path recomputation.
- Template hydration, repair, catalog priming, and settings backup follow the approved local-first boundaries.
- Marketing version and embedded-target metadata are 1.4.0 build 1.
- The real file-backed v1.3 migration fixture passes against the 1.4 four-store topology.
- Focused tests, the complete test suite, Release build, Analyze, signed Dev install, UI smoke tests, and targeted performance validation complete without release-blocking failures.
- The Production installation and its real data are never mutated during development validation.
